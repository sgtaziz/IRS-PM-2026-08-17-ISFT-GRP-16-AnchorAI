## Auth and app database (C5)

**AUTH-1 · Medium · fixed by A (`dafeb78`) · `Dockerfile` CMD, `catalog.py` seed**
- **Defect:** the API container runs `db seed --demo` on every start, and the seed re-inserted any missing seeded offer. A restart therefore brought back an offer an admin had deleted, with no audit entry for the re-insert.
- **Reproduced:** delete `checkin_message` → "restart" (upgrade + seed) → the offer was back. The audit log showed only `offer.delete`.
- **Fix (A):** offers are now seeded only into an empty catalogue, and a regression test was added.
- **For C:** consider `db seed --if-empty` in the CMD as well.

**AUTH-2 · Low · `api/deps.py:39-41`, `auth/security.py:42-44`**
- **Defect:** reactivating a user brings their old tokens back, because the `pwv` stamp depends only on the password hash.
- **Reproduced:** `/me` with a staff token gave 200; after deactivation, 401; after reactivation, 200 again with the same token.
- **Fix:** a `token_version` column (plus migration), bumped on deactivation and on password reset, and included in the stamp.

**AUTH-3 · Low · `auth/users.py:81-90`**
- **Defect:** creating the same username twice at the same moment returns 500, because the unique-index `IntegrityError` isn't caught after the bcrypt delay.
- **Reproduced:** with a parallel insert during the hash, the response was 500.
- **Fix:** catch `IntegrityError`, roll back, and raise `UserConflict` (409).

**AUTH-4 · Low · `api/routers/admin_audit.py:17`, `api/routers/users.py:28,38`**
- **Defect:** integers too large for SQLite cause a 500.
- **Reproduced:** `offset=1e20`, `PATCH /api/admin/users/1e20` and `POST …/1e20/password` all returned 500; the control, `PATCH …/999`, returned 404.
- **Fix:** add `le=2**63-1` to these parameters.

**AUTH-5 · Low · `frontend/src/pages/AuditLog.vue:60,69-71`**
- **Defect:** the CSV export keeps only `after ?? before`, so a role change exports the new role but loses the old one. W44 asks for both.
- **Fix:** export separate `before` and `after` columns.

**AUTH-6 · Low · `auth/security.py:21`, `tests/conftest.py`**
- **Defect:** tests hash with production bcrypt cost (`gensalt()` is 12 rounds, about 0.26 s per login). This is most of the suite's 48 s; AGENTS.md asks for seconds.
- **Missing test:** "a deactivated user's existing token gets 401" (`deps.py:36-42`).
- **Fix:** an autouse fixture that patches `bcrypt.gensalt` to 4 rounds (the dummy hash follows, so login-timing parity holds), plus that test.

**AUTH-7 · Low · `frontend/src/api/client.ts:42`, `router.ts`**
- **Defect:** the frontend's auth state never re-syncs. A 401 ends the session only if that request carried a token, and `user` is never refetched.
- **Consequences:**
  - logging out in one tab leaves the other tab showing errors, not the login page
  - logging in as someone else in one tab leaves stale nav in another
  - a demoted manager keeps nav entries that return 403
- **Server side:** stays correct in all three cases.
- **Fix:**
  - treat any 401 except `/auth/login` as the end of the session
  - listen for `storage` events on the token key
  - refetch `/me` on 403

**AUTH-8 · Low · `db/seeds/base.py:3-4`, `frontend/src/pages/Login.vue:100`**
- **Defect:** the docstring says users are "upserted", but existing users are kept, so changing `ANCHORAI_DEMO_PASSWORD` has no effect on an existing database. The login hint always shows `anchorai`.
- **Fix:** correct the docstring, and change the hint to "set by ANCHORAI_DEMO_PASSWORD (default anchorai)".

**AUTH-9 · Low · audit action names**
- **Defect:** C uses `user_create`, `user_update`, `rule_version_create` and `assistant_feedback`, while the rest of the app uses `<entity>.<verb>` (`offer.create`, `kg.reload`, `gym.*`). `AuditLog.vue:38` splits on `.`, so C's actions never get their verb styling.
- **Fix:** rename them to `user.create` and so on.

**Also fixed by A during this review (`dafeb78`):** `catalog.list_staff` kept deactivated staff in the planning roster. It now lists active staff only, and editing a deactivated staff member's hours returns 404.

## Rule engine and rule base (C1, C2, W40)

**RULE-1 · High · `reasoning/validate.py:65-82`**
- **Defect:** four of the eight derive rules can't be disabled. `asserted` is built from enabled rules only, but the unknown-fact check loops over all rules, disabled ones included.
- **Effect:** turning off D01, D02, D05 or D06 is rejected with "Unknown fact …". It is still rejected after first disabling the only playbook that reads the fact, because the error is raised on that disabled playbook. Nor can D03 and D04, or D07 and D08, both be off. The user guide documents the toggle as *the* way to disable a rule.
- **Reproduced:** through the real router: disable P04 gave 200, then disable D06 gave 422 "Unknown fact 'social_member'"; disable D07 gave 200, then D08 gave 422.
- **Fix:**
  - build `asserted` from all rules for the unknown-fact check
  - skip the conditions of disabled rules
  - report "only asserted by a disabled rule" as a warning

**RULE-2 · Medium · `reasoning/facts.py:48-58`, `rules/guardrails.yaml`**
- **Defect:** the contact-fatigue guardrails can't see real contacts or the admin's caps.
  - `days_since_last_contact` and `offers_last_90d` come only from the synthetic `interventions` table, as of `AS_OF`.
  - G01/G02 hard-code 30 days and 2 offers.
  - Nothing reads the W41 settings `max_contacts_per_member_per_30d` and `max_offers_per_member_per_90d`.
- **Effect:**
  - once B logs contacts, a member contacted yesterday is "allowed" again
  - the admin's cap fields change nothing
  - G02 can't fire at all on scenario data, because the history contacts each member at most once
- **Fix:**
  - build the contact facts from interventions plus approved plan items and outcomes
  - drive G01/G02 from the W41 settings
- **Offer from A:** we can add repeat contacts to the scenario history if C wants G02 exercised in E6.

**RULE-3 · Medium · `rules/playbook.yaml`, `reasoning/models.py:22`**
- **Defect:** SMS and calls are proposed to members with no phone on file. No rule reads `phone`, and a guardrail can't block a channel.
- **Reproduced:** 386 members have `phone == 0`; they receive 215 allowed SMS or call proposals.
- **Fix:** either
  - add `phone == 1` to the SMS/call playbooks, with email or in-person fallbacks; or
  - support channel blocks and add a guardrail.

**RULE-4 · Medium · `reasoning/validate.py:51-125`**
- **Defect:** the validator passes rules that can never fire. It ignores fact types and known category values, never checks a rule's own conditions against each other, and never checks playbooks against guardrails.
- **Examples that validate clean:**
  - `risk_band == High`
  - `risk_band >= 0.6`
  - `lifetime > 5` together with `lifetime < 3`
  - a playbook that G04 always blocks
- **Reproduced:** each case got an empty issue list.
- **Fix:**
  - type-check literals against `FactSpec`
  - check category values (risk band, segment names)
  - run `_satisfiable` on each rule
  - warn when a playbook is always blocked

**RULE-5 · Medium · `reasoning/service.py:58-60`, `validate.py:94-102`**
- **Defect:** rule output ignores the live offer catalogue.
- **Reproduced:**
  - After an admin deactivates `free_pt_session`, Member 360 still lists it under allowed offers, and its draft button then gets 409.
  - A playbook proposing `free_pt_session` by `sms` validates clean, although the catalogue allows only call or in person.
- **Fix:**
  - pass the active offers and their channels into validation and tracing
  - warn on an inactive offer, error on an unsupported channel

**RULE-6 · Medium · offer eligibility**
- **Defect:** free PT eligibility isn't enforced. The catalogue says "Members without PT in the last 90 days", but no fact or guardrail checks it (G03 does this for the discount).
- **Reproduced:** 36 of the 353 members who had a free PT session in the last 90 days are allowed another.
- **Fix:** add a `pt_last_90d` fact and a guardrail that blocks `free_pt_session`.

**RULE-7 · Medium · `db/seeds/base.py:42`, `frontend/src/diff.ts`**
- **Defect:** version Compare marks every rule as changed against the seeded version. v1 stores the raw rule files (with comments, in flow style), while every later save stores canonical YAML, and the UI diffs text.
- **Reproduced:** with C's real `diff.ts`, a v2 that differs from v1 only by disabling G04 shows "changed 20 of 20 rules, 239 of 321 lines". The rule-level comparison finds only G04.
- **Fix:** either
  - seed v1 as `dump_rules(load_rule_files())`; or
  - compare parsed rules (the backend `_diff`).

**RULE-8 · Low · `reasoning/versions.py:282-306`**
- **Defect:** the stale-version check in `save_version` isn't atomic. A rollback committed between B's check and B's write is silently overwritten (reproduced with an injected interleaving).
- **Fix:** use a conditional `UPDATE … WHERE is_active AND version = base_version` and require rowcount 1.

**RULE-9 · Low · `validate.py:68`, `models.py:20`**
- **Defect:** an assert with a list value (`assert: {tags: [a, b]}`) makes Validate and Save return 500 (unhashable type).
- **Fix:** type the assert value as `bool | int | float | str`.

**RULE-10 · Low · `models.py:38,44`**
- **Defect:** the rule id and the mandatory `source` accept blanks or whitespace, and ids with `/` can't be addressed by `PATCH /api/rules/{rule_id}`.
- **Fix:** strip and set a minimum length on both, and give ids a pattern such as `^[A-Za-z0-9_]+$`.

**RULE-11 · Low · type-handling edge cases**
- **(a) yes/no:** `assert: {x: yes}` is read by YAML as `True`, while `x == yes` compares to the string `'yes'`, so the rule never fires.
- **(b) commas:** commas inside quoted list items break `in [...]` parsing (latent: no segment name has a comma).
- **(c) numbers in the form:** a numeric derived fact is typed "category" in the form (`versions.py:174`), so the form saves `"3"` as a string. This one was found by code trace.

**RULE-12 · Low · wording: `RulesAdmin.vue:282`, `user-guide.md:299`, `engine.py:48-49`, `validate.py:122`**
- **Defect:** the docs say "guardrails fire first", but the order is salience, then number of conditions, then file order, whatever the kind. Guardrails win only because blocks are applied after the loop. The comments also say the higher-priority value wins, but with chaining it's the first assertion that wins.
- **Fix:** correct the wording in all four places.

**RULE-13 · Low · `RulesAdmin.vue:292`**
- **Defect:** a broken active version locks the admin out of rollback in the UI. `GET /api/rules` and `/vocabulary` return 500 when the active YAML no longer parses, and the Versions and YAML tabs sit inside that page's error state. The backend repair path works (`/versions` gives 200).
- **Fix:** render those tabs outside that PageState.

**RULE-14 · Low · `derive.yaml:44-50`, `playbook.yaml:59-65`**

  - D06 says "partner company or a friend" but tests only `promo_friends`.
  - P08 says "any other medium-risk member" but fires for every medium-risk member.

- **(b)** `tests/fixtures/rule_cases.yaml:47-58` uses fee and contract pairs the data never produces: a 1-month contract at 50, and a 6-month contract at 45 (fees are 72, 54 and 46).

## Knowledge graph (C3, W18)

**KG-1 · Medium · `knowledge/reload.py:40-60`, `knowledge/signals.py:56-59`**
- **Defect:** the KG status says "fresh" when the rules have already dropped the KG facts. `status()` checks only process memory and gym edits, while `load_kg_facts()` ignores facts older than `model_card.json`.
- **Effect:** after a data build, or on a fresh clone without Neo4j:
  - D07 and D08 stop firing, and explanations lose their graph signals
  - yet `/api/admin/kg/status` says `stale: false` and simulate says `graph_out_of_date: false`
- **Reproduced:** M0002's trace fires D07 with fresh facts. After making the model card newer, D07 is gone while both flags still say not stale.
- **Fix:** derive staleness from the files: no `kg_facts.parquet`, or one older than the model card, means stale, with its own message.

**KG-2 · Low · `cli.py` `kg_load`, `reload.py:72-76`, `graph.py:9`**
- **Defect:** `kg load` prints "Neo4j is not reachable; skipped" and exits 0 for every `GraphDown`, which also wraps:
  - `DataNotBuilt`
  - Cypher or driver errors after `CLEAR` has already emptied the graph
  - `AuthError` (a wrong password)
- **Reproduced:** with a missing model card, it printed "not reachable" and exited 0. The Cypher and auth paths were checked by code trace.
- **Fix:** print the real cause, and fail (exit 1) on load errors, skipping only on real unreachability.

**KG-3 · Low · `reload.py:65-76`**
- **Defect:** `sync_graph()` says it never raises, but `get_driver()` is outside the `try`.
- **Reproduced:** with `NEO4J_URI=localhost:7687`, `sync_graph()` raised `ConfigurationError`.
- **Effect:** a saved roster edit would return 500, and the A data rebuild would be marked "failed" although the data was rebuilt.
- **Fix:** move `get_driver()` inside the `try` and catch broadly in `sync_graph`.

**KG-4 · Low · fixed by A (`b48acf0`):** the same fixture leak as RULE-16.

**KG-5 · Low · `knowledge/queries.py:3-11`, `reasoning/facts.py:33-35`**
- **Defect:** `anchor_instructor_share` sums the visits of *all* departed instructors, but the fact label, D07 and the explanation text describe one "anchor" instructor. Two departures of 30% each give 0.6, and D07 then says most visits were with "an instructor who has left".
- **Note:** A's ground truth (`true_churn.lost_instructor_share`) uses the same summed definition on purpose, so either fix keeps the two consistent.
- **Fix:** either take the maximum per instructor, or relabel as "share of visits with departed instructors".

**KG-6 · Low · `knowledge/loader.py:150-158`**
- **Defect:** a reload isn't atomic for readers. `CLEAR` and each batch commit separately, and every roster edit triggers a full synchronous reload.
- **Effect:** a concurrent ego, simulate or assistant read can see an empty or partial graph (for example, the ego endpoint returns 404 "not in the knowledge graph").
- **Fix:** return 503 "reloading" while the reload lock is held, or load under a build id and swap.

## Checked and OK (coverage)

- **Auth:**
  - **JWT:** HS256 pinned; `alg=none`, HS512, wrong key, expired token, missing `pwv` and string `uid` are all rejected.
  - **Passwords:** bcrypt with the 72-byte limit checked in bytes.
  - **Login:** the same 401 and the same timing (about 263–275 ms medians) for known, unknown and inactive users.
  - **Roles:** all 54 routes enumerated; every write route has a role dependency.
  - **Admins:** last-admin and self-demotion guards work, including a concurrent mutual deactivation.
  - **Leaks:** no password hash in any response or audit row.
- **App database:**
  - **Migrations:** single head; upgrade → downgrade → upgrade is clean; `alembic check` finds no drift.
  - **Seeds:** byte-identical (apart from hashes and timestamps) across runs.
  - **Integrity:** SQLite foreign keys enforced, and the session is request-scoped.
- **Rule engine:**
  - **Agenda:** recomputed each cycle; refraction by rule id; terminates; derived facts feed later rules.
  - **Order:** total and deterministic (salience, specificity, file position).
  - **Guardrails:** blocks applied after the loop, so they override playbooks.
  - **Conditions:** no `eval`/`exec`, with clear errors for malformed ones.
  - **Versioning:** activation is a conditional UPDATE plus a single-active check.
  - **Audit and roles:** every rule write is audited and admin-only.
- **Rule base vs Stream A facts:**
  - `trend_ratio`, `lifetime` (months), `contract_period`, `monthly_value` and the risk-band names are all used correctly.
  - Every rule has a source.
  - The simulated interviews are clearly marked as AI-simulated (the report must say no practitioner was interviewed).
- **Knowledge graph:**
  - **Cypher:** every query is a static template with values as parameters.
  - **Reads:** go through read sessions.
  - **Loader:** idempotent (MERGE, uniqueness constraints, batched `CLEAR` of stale nodes).
  - **Neo4j down:** degrades as PLAN asks: 503 on graph endpoints, edits saved and marked stale, and `setup` doesn't abort.
  - **Admin overlay:** validated and audited, and suppressions survive rebuilds.
- **AGENTS.md:** ruff clean, no TODOs, comments explain why, tests offline with Neo4j mocked.
